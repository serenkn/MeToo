## 1. コスト方針

**原則：ユーザーが増えて無料枠を超えるまで、月額0円で運用する。**
収益化はインフラコストが発生し始めるタイミングで導入する（無料プラン広告＋有料サブスク）。

-----

## 2. 各サービスの無料枠と課金モデル

|サービス             |無料枠                                |超過時の挙動                          |カード登録 |
|-----------------|-----------------------------------|--------------------------------|------|
|Neon             |ストレージ0.5GB / 月100 CU時間 / 転送5GB/月   |**停止する**（その月のDB計算が止まる。勝手に課金されない）|不要    |
|Vercel Hobby     |帯域100GB/月・関数実行制限                   |**停止する**（課金されない）                |不要    |
|Pusher Sandbox   |同時接続200 / 20万メッセージ/日               |**制限される**（課金されない）               |不要    |
|Cloudflare R2    |10GB / 書込100万回 / 読込1000万回（月）/ 転送料ゼロ|⚠️ **自動で従量課金が始まる**（$0.015/GB）    |**必要**|
|NextAuth / Prisma|ライブラリのため完全無料                       |—                               |—     |
|Google Maps      |**API不使用**（後述）                     |—                               |—     |

### ⚠️ R2だけが従量課金である点に注意

- R2の有効化にはカード登録が必須。無料枠超過時は停止ではなく**自動課金**される
- 対策1：Cloudflareダッシュボードで**使用量通知（Notifications）を必ず設定**する
- 対策2：画像はアップロード前にクライアント側で圧縮（後述）。10GB＝圧縮済み画像で数万枚相当なので、MVP期に超えることは現実的にない

### 地図はAPIを使わない（決定事項）

- 募集詳細の集合場所は「住所表示＋**Googleマップで開くリンク**」のみとする
- リンク形式：`https://www.google.com/maps/search/?api=1&query={緯度},{経度}`（API不要・無料・キー不要）
- 理由：2025年3月にGoogle Maps APIの$200クレジットが廃止され、地図表示は月1万回までに変更された。埋め込み地図は募集詳細のPVに比例して枠を消費するため、MVP期の最大の課金リスクだった
- 将来、収益化後に埋め込み地図へ戻すかを再検討する

## 3. ボトルネック分析（どこから詰まるか）

|順位|ボトルネック         |内容                                        |目安        |
|--|---------------|------------------------------------------|----------|
|1 |NeonのCU時間（月100）|アクセスが常時あると消費が早い。0.25CUで月400時間相当           |DAU数百人までは可|
|2 |Neonの0.5GB     |メッセージが最も容量を食う。テキストのみなら数十万件は可              |MVP期は問題なし |
|3 |Pusher同時接続200  |トークルーム表示中のみ購読する設計のため、同時に200人がトーク画面を開かない限り可|MVP期は問題なし |
|4 |Vercel帯域100GB  |画像はR2配信（転送料ゼロ）のためVercel帯域をほぼ消費しない         |問題になりにくい  |

※ Neonのスケールゼロ復帰時に**コールドスタート（0.5〜2秒）**が発生する。MVP期は許容し、課金フェーズで`scale to zero`無効化（有料）を検討。

## 4. コスト最適化ルール（実装時に必ず守る）

1. **画像はアップロード前にクライアント側で圧縮する**
- 長辺1080pxにリサイズ・JPEG品質80%程度
- R2の容量と読込回数、アップロード帯域をすべて節約
1. **メッセージ取得は必ずページネーション**（50件ずつ・無限スクロール）
- 全件取得はNeonのCU時間を無駄に消費する
1. **一覧系APIに短いキャッシュを入れる**（10〜30秒）
- Vercelの関数実行数とNeonの起動回数を両方削減
1. **Pusherの購読はトークルーム表示中のみ**
- 画面を離れたら必ずunsubscribeする
1. **DBにバイナリを保存しない**
- 画像は必ずR2、DBにはURLのみ（決定済み）

## 5. AI開発体制（モデル使い分け）

**方針：賢さをドキュメントとルールに前払いし、日常の実装は下位モデルで回す。**

### モデルの役割分担

|モデル      |担当                          |頻度       |
|---------|----------------------------|---------|
|Fable（上位）|設計判断・アーキテクチャ変更・大きなレビュー      |月数回      |
|Opus     |日常の実装・修正・テスト作成（Claude Code） |メイン      |
|Sonnet   |定義済みの小タスク（コンポーネント1個・API1本など）|コスト削減したい時|

### 下位モデルで品質を保つための構造

1. **`CLAUDE.md`をリポジトリ直下に置く**（Claude Codeが起動時に自動で読む）
- 「作業前にdocs/を読む」指示
- Bulletproof規律（feature間の直接import禁止・index.ts経由のみ・app/は薄く）
- コマンド一覧（dev / build / lint / migrate など）
- コーディング規約
1. **タスクは小さく具体的に切る**
- ×「認証機能を作って」
- ○「docs/01のS02仕様に従ってログイン画面を実装して」
1. **ガードレールを機械化する**（人間ではなくツールがミスを捕まえる）
- TypeScript strictモード
- ESLintでfeature間importを機械的に禁止
- Prisma schemaをDB定義の唯一の正とする
- CI（GitHub Actions）でPRごとにtypecheck / lint / testを自動実行

### docs/の役割

- 設計書一式（01〜06）が下位モデルへの「文脈の引き継ぎ書」を兼ねる
- 設計を変更したら**必ずdocs/を先に更新**してから実装する（ドキュメントと実装のズレが下位モデルを最も混乱させる）

## 7. 運用保守のAI自動化

**核となるループ：エラー → Issue → AIが修正PR → CI検証 → 人間がマージ**

### 構成

|役割    |ツール                                       |コスト  |
|------|------------------------------------------|-----|
|エラー監視 |Sentry（GitHub連携）                          |無料枠あり|
|死活監視  |UptimeRobot                               |無料   |
|自動起票  |Sentry → GitHub Issue 連携                  |無料   |
|修正PR作成|Claude Code Action（GitHub Actions）        |API従量|
|検証    |GitHub Actions CI（typecheck / lint / vitest）|無料枠内 |
|依存更新  |Renovate（更新PR自動作成）                        |無料   |
|デプロイ  |Vercel（mainマージで自動）                        |無料   |

### フロー

1. **検知**：Sentryが本番エラーを捕捉、UptimeRobotがダウンを検知
1. **起票**：SentryのGitHub連携でエラーが自動でIssue化される
1. **修正**：Issueに`@claude`をメンション → Claude Code ActionがCLAUDE.mdとdocs/を読み、修正PRを自動作成
1. **検証**：CIがPRに対してtypecheck・lint・testを自動実行
1. **承認**：**マージとデプロイの判断は必ず人間**。mainマージでVercelが自動デプロイ

### 定期メンテナンス

- Renovateが依存パッケージの更新PRを自動作成 → CI通過後に`@claude`にレビューさせてから人間がマージ
- GitHub Actionsのスケジュール実行（週1）でClaudeにエラー傾向の要約Issueを書かせる

### AIに任せない領域（安全線）

- **Neon / Cloudflare / Vercelのダッシュボード操作・カード情報・シークレット管理は人間のみ**
- **mainブランチは保護し、自動マージは絶対にしない**
- 本番障害の即応は不可（検知〜修正PRまでは自動でも、マージ判断は人間の起きている時間になる）
- AIのCI実行にDBの本番認証情報を渡さない（テストはモック or 専用のテスト用ブランチDBを使う）

## 8. 課金フェーズへの移行判断

以下のいずれかに達したら収益化とインフラ課金を検討する：

- NeonのCU時間が月の途中で尽きる状態が2ヶ月続く
- Pusherの同時接続が日常的に150を超える
- Vercelの商用利用ポリシーが問題になる規模になる（→ Cloudflare Pages移行 or Vercel Pro $20/月）

移行時の想定コスト：Vercel Pro $20 ＋ Neon Launch $5〜 ＋ Pusher Startup $49 ＝ **月$75前後**から。
このコストを賄える収益（サブスク or 広告）の設計を、移行の3ヶ月前から始める。
